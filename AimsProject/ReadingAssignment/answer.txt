9. <?> When should accessor methods be used?
Theo tác giả Allen Holub, việc sử dụng các phương thức truy cập nên được sử dụng hạn chế tối đa nhằm bảo vệ tính đóng gói trong lập trình hướng đối tượng.
Tuy nhiên vẫn có các trường hợp cụ thể mà ông khuyên dùng vì cần thiết và hợp lí:
- Khi trả về 1 đối tượng dưới dạng Interface:
    + Điều này giúp cô lập các thay đổi. Lập trình viên không cần chỉnh sửa quá nhiều khi 1 trong các thuộc tính của lớp cần cập nhật hoặc thay đổi, chỉ cần điều chỉnh định nghĩa của đối tượng được trả về để khớp với Interface là được.
- Khi giao tiếp với các lớp thuộc tầng ranh giới (Procedural Boundary Layers):
    + Các chương trình hướng đối tượng thường phải giao tiếp với các hệ thống thủ tục như hệ điều hành hoặc cơ sở dữ liệu, điển hình là JDBC.
    + Do các nhà phát triển thư viện không thể dự đoán trước chính xác mục đích sử dụng dữ liệu của lập trình viên, họ buộc phải sử dụng các accessor để đảm bảo tính linh hoạt cần thiết khi sử dụng.
- Trong các gói thư viện Java dùng chung (Generic Java Packages):
    + Cũng giống với tầng ranh giới, các gói thư viện này phải được thiết kế với tính linh hoạt cao để phù hợp với mọi hoàn cảnh và mục đích sử dụng của lập trình viên sau này.
    + Mặc dù các nhà phát triển luôn cố gắng ẩn đi càng nhiều chi tiết cài đặt bên trong càng tốt nhưng accessor vẫn là công cụ cần thiết để cung cấp khả năng truy cập dữ liệu cho người dùng. Đặc biệt là khi họ không thể dự đoán được mô hình động mà người dùng sử dụng.
- Sử dụng cho các công cụ tự động và Introspection như JavaBeans:
    + Accessor được tạo ra nhằm đánh dấu (tag) các thuộc tính để các công cụ tự động như UI-builders có thể nhận diện chúng thông qua cơ chế Introspection/Reflection.
    + Tuy nhiên, các lập trình viên không được khuyến khích sử dụng các phương thức này vì dễ gây ảnh hưởng đến hệ thống, các phương thức này được tạo ra chỉ dành cho các công cụ tự động sử dụng thôi.

        Suppose we are taking this Comparable interface approach.

        - Can we have two ordering rules of the item (by title then cost and by cost then title) if we use this

        - Suppose the DVDs have a different ordering rule from the other media types, that is by title, then

C1: Lớp nào nên thực hiện (implement) interface Comparable?
    Lớp Media nên thực hiện Comparable<Media> và ghi đè phương thức compareTo().

C2: Cách hiện thực phương thức compareTo() để phản ánh thứ tự mong muốn?
    Ta ghi đè phương thức compareTo() trong lớp Media.
    Giả sử thứ tự ưu tiên là Tiêu đề (Title) trước, sau đó đến Giá tiền (Cost).

    @Override
    public int compareTo(Media other) {
        // So sánh tiêu đề trước
        int titleDiff = this.getTitle().compareToIgnoreCase(other.getTitle());

        if (titleDiff != 0) {
            return titleDiff;
        }

        // Nếu tiêu đề giống nhau, ta so sánh đến giá tiền
        return Float.compare(other.getCost(), this.getCost());
    }

C3: Dùng Comparable có thể có 2 quy tắc sắp xếp khác nhau không?
    Không thể. Comparable dùng để định nghĩa một thứ tự tự nhiên (natural ordering) duy nhất cho lớp. Để có nhiều quy tắc sắp xếp, ta dùng Comparator.

C4: Nếu DVDs có quy tắc sắp xếp riêng (Title -> Length giảm dần -> Cost) thì code cần điều chỉnh gì?
    Khi sử dụng hướng tiếp cận Comparable ở lớp cha, ta có thể sửa đổi code trong phương thức compareTo() của lớp Media bằng cách sử dụng kiểm tra kiểu dữ liệu (instanceof).

    Cách thực hiện:

    Java
    @Override
    public int compareTo(Media other) {
        // So sánh tiêu đề, áp dụng cho tất cả Media
        int titleDiff = this.getTitle().compareToIgnoreCase(other.getTitle());
        if (titleDiff != 0) return titleDiff;

        // Nếu cả hai đều là DVD, so sánh thêm độ dài giảm dần
        if (this instanceof DigitalVideoDisc && other instanceof DigitalVideoDisc) {
            DigitalVideoDisc dvd1 = (DigitalVideoDisc) this;
            DigitalVideoDisc dvd2 = (DigitalVideoDisc) other;

            int lengthDiff = Integer.compare(dvd2.getLength(), dvd1.getLength());
            if (lengthDiff != 0) return lengthDiff;
        }

        // So sánh giá
        return Float.compare(other.getCost(), this.getCost());
    }

<?> 11.  The Aims class must be updated to handle any exceptions generated when the play() methods
        are called. What happens when you don’t update for them to catch?

If we do not update the Aims class to catch the exceptions generated by the play() methods, two main things will happen:
1. Compile-time Error: Since PlayerException is a custom exception extending java.lang.Exception (which makes it a "checked exception"), the Java compiler enforces a strict "catch or specify" requirement. If we call play() without enclosing it in a try-catch block (or declaring it in the method signature with the 'throws' keyword), the program will fail to compile and throw an error: "unreported exception PlayerException; must be caught or declared to be thrown".
2. Abrupt Termination (Runtime Crash): Even if we somehow bypassed the compiler (e.g., by making it a RuntimeException), if the exception is not handled (caught) during runtime when a media with a non-positive length is played, the exception will propagate up the call stack. Once it reaches the JVM without being caught, it will cause the entire application to crash (terminate abruptly) and dump an ugly stack trace to the console, leading to a poor and disruptive user experience.
